# CIS 295 — Course Development

## What This Is

Course materials for CIS 295 (Web Development II) at Central Oregon Community College, Winter 2027
(January 4 – March 19, 2027; 11 weeks including Finals Week).

See `course-outline.md` for the full 11-week outline and `alignment-doc.md` for the week-by-week
outcome alignment map.

## Course Catalog Description

This outline must fulfill the information
[published in the COCC catalog](https://catalog.cocc.edu/course-outlines/cis-295/).

### Course Description

Gain a deeper understanding of HTML (for structure) and CSS (for style) while creating multi-page
websites suitable for businesses and organizations. Explore web development's more advanced
techniques useful for improving usability and user experience. Plan and design websites for desktop
and mobile users.

- **Credits:** 4 (50 contact hours: 30 lecture / 20 other)
- **Recommended preparation:** [CIS 195](https://catalog.cocc.edu/course-outlines/cis-195/) (Web
  Development I)

### Course Learning Outcomes

1. Utilize the most recent HTML elements and CSS properties to create and style webpage content.
2. Plan, construct, and style webpage layouts for multiple devices and users.
3. Construct website features commonly found on large website projects.
4. Integrate site management concepts such as SEO and accessibility into a website’s plan, layout,
   and design.

### Content Outline

- Usability and user experience
- Mobile web design
- Advanced HTML elements and CSS properties
- Efficient HTML/CSS syntax
- CSS extension languages
- Large-scale navigation menus
- Search Engine Optimization (SEO)
- Designing web forms
- Web developer’s portfolio

## Key Decisions

### Pedagogical Approach

- **Modern native HTML & CSS first.** Teach current web platform capabilities—semantic landmarks,
  CSS custom properties, `@layer`, native nesting, Grid/Subgrid, Container Queries, `<dialog>`,
  Popover API, `<details name="...">`, and native form validation—rather than workarounds left over
  from older curricula.
- **No overlap with CIS 133JS.** CIS 133JS is a separate 4-credit course requiring CIS 122. CIS 295
  only recommends CIS 195. Keep JavaScript minimal and strictly progressive-enhancement (for
  example, calling `dialog.showModal()` or toggling a mobile drawer when needed), never assuming
  prior programming coursework.
- **Modern CSS extension languages & frameworks.** Explain Sass and PostCSS conceptually in Week 2
  so students recognize them in existing codebases and understand what native CSS has absorbed. Give
  students one hands-on week with **Tailwind CSS v4** in Week 7 alongside shared multi-page layout
  patterns.
- **Version control and automated deployment replace FTP.** Git/GitHub PR workflows and automated
  deploys to CloudFront via GitHub Actions start in Week 1. Mention SFTP briefly as legacy shared
  hosting context only.
- **Accessibility and performance are engineering disciplines, not checklists.** DevTools (Grid/Flex
  overlays, Accessibility Tree, Lighthouse, Network throttling) and axe DevTools are woven across
  the term.

### Student Background & Onboarding

- Recommended prep is CIS 195 (basic HTML/CSS, folder/file management, publishing pages). Do not
  assume CLI fluency, WSL, `nodenv`, or programming background.
- **Low-friction Week 1 path:** Lead with **GitHub Desktop** or **VS Code Source Control** (HTTPS
  browser sign-in, no SSH keys required) and standard cross-platform Node LTS, with CLI Git and
  GitHub Codespaces documented as optional paths.
- Keep the Git loop small and consistent every week: `clone` -> `branch` -> `commit` -> `push` ->
  `open PR` (with `artzte` as reviewer).

### Starter Kit & Tooling

- **Vite** (multi-page HTML dev server + build, near-zero config)
- **Prettier** (consistent formatting) + lightweight HTML/CSS linting (`html-validate`, `stylelint`)
- **GitHub Actions -> AWS CloudFront** course hosting (live preview URL for every student)
- **Tailwind CSS v4** (`@tailwindcss/vite`) introduced in Week 7; pure modern native CSS in Weeks
  1–6
- Standard scripts from Day 1: `npm run dev`, `npm run build`, `npm run lint`, `npm run format`

### Assessment & AI Policy

- **Grading weights:** Weekly Quizzes 20% (10 short-essay quizzes), Weekly Assignments 40% (1 bye
  week allowed), Final Project 40% (4 equal milestones). No midterm or final exam.
- **Late work:** Accepted without penalty through Week 10 (before Finals Week).
- **Student AI policy:** Students may not use GenAI to produce assignments, quizzes, or the final
  project. Two explicit exceptions: (1) troubleshooting local IT/environment setup issues (Git,
  Node, VS Code), and (2) using **any AI agent to perform an adversarial code/PR review** (pointing
  out logical flaws, HTML/CSS/accessibility issues, and syntax problems without providing full
  rewrites). Include the suggested review prompt in the syllabus and README, plus full transparency
  on instructor use of AI to draft course materials.

### Final Project & Portfolio

- **Final Project (40% of grade, 4 milestones):** A complete, responsive, accessible, SEO-ready
  **multi-page business or organization website** (at least 4 distinct pages), deployed to
  CloudFront.
  - Milestone 1 (Week 3, due Mon Jan 25): Proposal (`projects/final/README.md`)
  - Milestone 2 (Week 6, due Mon Feb 15): Design Document (site map, wireframes, design tokens,
    contrast audit, form spec)
  - Milestone 3 (Week 8, due Mon Mar 1): Initial Structure & Test Deployment (live CloudFront URL)
  - Milestone 4 (Week 11, Finals Week): Initial PR Mon Mar 15 -> comments Wed Mar 17 -> approval Fri
    Mar 19
- **Developer Portfolio (Week 9):** Built and deployed as the student's personal showcase linking
  their live CloudFront business site and selected weekly projects, fulfilling the catalog's "Web
  developer's portfolio" requirement cleanly without crowding the business-site capstone.

## Authoring Conventions for Weekly Content

Follow the same repo layout and authoring conventions established in `cocc-js`:

### Weekly Module Layout

Each week has a `modules/weekN/` folder with an overview, module lecture page(s), a quiz, and an
assignment. Matching lecture guides go in `lectures/`, starter fixtures and DevTools examples go in
`examples/`, and reading summaries go in `weekly-readings/week-NN.md`. Do not commit generated
`.html`, `.pdf`, or `.qti.zip` build outputs from Kerplunk (except `modules/syllabus/syllabus.pdf`).

### Quizzes

- Five short-essay questions. Each asks for **one thing**: one definition, one comparison, or one
  explanation in the student's own words.
- Do not stack sub-questions. If a reading lists several items, ask for **one**.
- Avoid trivia and predict-the-output puzzles; point students back to the linked reading ("as
  discussed in [reading link]").
- At most one question per quiz should reference the assignment, focusing on the concept behind it.

### Assignments

- **Keep the scope small and focused** on the week's concept. Leave out stretch requirements and
  long reflection essays (quizzes cover reflection).
- **Hand over the busywork.** Put sample copy, images, and messy starter HTML/CSS fixtures in
  `examples/` so students spend their time practicing the target skill, not inventing placeholder
  paragraphs.
- **Accept more than one valid implementation** where appropriate (e.g., CSS Grid track sizing
  choices, semantic structure variations that still pass accessibility checks).
- **Write requirements as nested bullet lists**, not dense paragraphs.
- Standard submission loop: branch, scaffold folder, `npm run dev` / `npm run lint` /
  `npm run format`, open PR with **artzte** as reviewer, submit PR URL on Canvas.

### HTML & CSS Style in Examples and Solutions

- Semantic HTML first (`<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<aside>`,
  `<footer>`, single `<h1>` per page, proper heading order).
- Prefer native interactive elements (`<button>`, `<a>`, `<dialog>`, `<details>`, `popover`) over
  `<div>` click handlers and unnecessary ARIA.
- Use CSS custom properties for tokens, `@layer` for cascade organization, logical properties where
  helpful, and `:focus-visible` for keyboard focus styling.
- Respect `prefers-reduced-motion` and `prefers-color-scheme`.

### Voice

- Write in a plain, direct, first-person instructor voice ("my preferred approach is…"). Go easy on
  bold text and marketing language.
- Keep instructions short and practical. A photographed pencil sketch linked in the README is a
  perfectly good wireframe.
